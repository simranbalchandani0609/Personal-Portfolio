MediCloud v2

Hospital appointments and encrypted records in one system.

The problem

A hospital needs one place where patients can book visits, doctors can see what they need before a consultation, and records stay private.

What it does

MediCloud v2 is a hospital appointment and encrypted-records system built for AWS. A React website talks to an Express API. Data is stored in DynamoDB, files go to S3 with KMS encryption, and SNS and CloudWatch handle notifications and monitoring, all in the Mumbai region (ap-south-1).

What works

  • Patients book slots and see their records. Doctors and admins each get their own views, plus a live audit trail.
  • DynamoDB conditional writes stop two people booking the same slot. Login uses JWT, bcrypt and role-based access.
  • v2 adds prescriptions, a health profile with vitals, a symptom check and doctor reviews. The symptom check uses simple built-in rules to suggest a type of doctor. It is not a diagnosis.

Testing: 82 API checks and 5 UI flows against a local emulator. The hosted AWS setup hasn't been tested end to end yet.

  • React
  • Node.js
  • Express
  • DynamoDB
  • S3 + KMS
  • SNS
  • CloudWatch
  • IAM
  • JWT
  • bcrypt
What I learned: DynamoDB's reserved words and safe rollbacks

While testing v2, a request failed with a 500 error. I traced it to an attribute I had named method. DynamoDB reserves that word, along with role and status, so it can't be used in a query expression as it is. The local emulator I tested with was more forgiving than real AWS. I fixed it by renaming the attribute, and now I alias those words with # placeholders in every expression.

The lesson was to check against the real service's rules instead of trusting the emulator. A check that passes locally doesn't prove it works on AWS.

A second lesson was about design. Making v2 only add new tables, and never change the shape of v1's data, is what makes rollback safe. Switching versions just means running a different folder, with no data migration.

Flight Management Dashboard

Flights, passengers, staff and ticket revenue in one place.

The problem

Flight status, passenger details, employee records and ticket revenue are easier to act on when they sit together, rather than in separate lists.

What it does

The dashboard brings flight, passenger, employee and ticket information into one view, so users can track flight status and analyse airline revenue. It is built with FastAPI, MySQL and Chart.js.

What works

  • Summary cards and interactive charts: delayed against on-time flights, flights per city and an airline breakdown.
  • A flight filter plus search and sortable tables for flights and passengers.
  • Options to add, update or delete records.
  • FastAPI
  • MySQL
  • Chart.js
  • JavaScript
  • CSS
What I learned: keeping filters, charts and tables in sync

One challenge was making sure the filters updated all the charts and tables consistently. Solving it helped me understand how the frontend connects to the FastAPI backend, and how to keep the dashboard in sync with the data.

Rajkot's restored lakes, seen from space

A before-and-after satellite study. No results yet.

The question

Rajkot's urban lakes, Atal Sarovar and the Aji–Nyari–Lalpari system, were restored, and the project has drawn plenty of design and architecture coverage. I haven't found a remote-sensing study that measures how much their surface water actually changed, so that is what I'm setting out to do.

The plan

Compare surface water before and after the restoration using satellite data. I'm drawing on the JRC Global Surface Water dataset (1984 to the present), Landsat 5, 8 and 9 and Sentinel-2 imagery through Google Earth Engine, and Rajkot Smart City's GIS ward boundaries.

  • Google Earth Engine
  • Landsat
  • Sentinel-2
  • JRC Global Surface Water
